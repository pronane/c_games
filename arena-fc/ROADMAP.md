# Arena FC — improvement roadmap (Oct 2026)

This document answers four questions raised after the first gameplay videos:

1. Why Godot cannot export **this** project to the web.
2. Why the players looked like dots — and what was changed.
3. What I can do with FBX character files you supply.
4. What it would take to look/play like a modern AAA football title, and how to make it
   playable online with friends.

Everything below assumes the standing constraints: original code/art only, no
FIFA/PES/eFootball assets, branding, likenesses, kits, audio or proprietary code.

---

## 1. Why the full game is not a Web export

Godot 4's web exporter builds a WebAssembly module from **GDScript + the engine**.
C# projects need the .NET/Mono runtime *inside* that WASM module. When Godot 4 moved
from the old Mono embedding API to .NET Core hosting (`hostfxr`), that runtime
could no longer be packaged for the browser, and desktop-only support shipped
first [13](https://godotengine.org/article/platform-state-in-csharp-for-godot-4-2/).
The official docs still state plainly: *"Projects written in C# using Godot 4
currently cannot be exported to the web"* [2](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html),
and the 4.7 editor still refuses it [4](https://forum.godotengine.org/t/cant-export-to-web/141491).

There **is** active work: a Web .NET prototype was shown at GodotCon Boston in
May 2025 [5](https://godotengine.org/article/live-from-godotcon-boston-web-dotnet-prototype/),
with draft PRs for a statically-linked Mono/LibGodot WASM runtime
[1](https://github.com/godotengine/godot/pull/106125),
[2](https://github.com/godotengine/godot/pull/118976). As of late 2026 those are
still draft/community builds with caveats — pinned Emscripten versions, invariant
globalization, threading/COOP-COEP requirements, no committed release date
[7](https://app.cinevva.com/guides/godot-vs-unity-web-games),
[10](https://github.com/gd-kirie/godot-dotnet-web-templates). Also, browser
networking has no raw UDP; only HTTP, WebSocket and WebRTC are available
[2](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html).

**Our workaround (already shipped):** `Web/BrowserBoot.gd` is a GDScript-only
Browser Edition that loads the *same* skinned rig data (`Data/rig_default.json`,
generated by the C# `RigBuilder`) and runs a lighter 5-a-side match. It exports
cleanly to WebGL 2 / WASM and runs in Chromium. It is a reduced game, not a port.

**If C# web export ever lands:** the desktop `Scripts/` tree can be exported
directly, and the separate GDScript edition can be retired. Until then, a second
option is to move gameplay-critical code into a C++ GDExtension, which *can* be
compiled to WASM — but that is a rewrite, not a config change.

## 2. "The players look like dots"

They are real 3D skinned meshes, not sprites: 18 bones, 2,045 vertices, 2,624
triangles, 9 PBR material surfaces, 4 bone weights per vertex, animated every
frame by `RigAnimator` writing quaternions into `Skeleton3D`. The problem in the
first videos was purely **framing** — the original broadcast camera sat 28 m up
and 46 m back, so a 1.8 m human was ~30 px tall at 720p.

**Shipped in this update:**

* Closer default broadcast camera (18 m / 34 m) and default zoom of 0.68 →
  players are roughly 1.5–2× larger on screen at kick-off.
* **Six camera views**, selected with `C` to cycle or `1`–`6` to jump directly:
  `Broadcast`, `Telephoto`, `Player cam`, `Tactical`, `Behind goal`, `Orbit`.
  Right-drag steers the Orbit view.
* **Continuous dolly zoom** (0.55×–2.4×) via mouse wheel, trackpad pinch,
  `+`/`-` (or numpad `+`/`-`), gamepad right stick, on-screen `+`/`−` buttons,
  and the camera buttons in the pause menu. The HUD shows `view · zoom %`.
* Default view and zoom are configurable in **Match Settings**, stored in
  `MatchOptions.CameraMode` / `CameraZoom`.
* **Selection ring**: a pulsing, distance-compensated double ring + soft disc
  under the controlled player and a floating arrow above the head
  (`Scripts/Godot/SelectionMarker.cs`). It stays visible from the 80 m tactical
  camera without becoming a giant triangle in the over-the-shoulder view.
* The same ring, four camera views and zoom were added to the GDScript Browser
  Edition so web and desktop match.

The honest remaining limit: the *mesh itself* is deliberately low-poly and built
from boxes/cylinders, because it is generated procedurally at runtime with no
external art. Zooming in makes that obvious. Fixing it needs real character art —
see the next section.

## 3. Yes — send FBX files and I can make realistic players

Godot 4.3+ imports `.fbx` directly through the built-in **ufbx** library (the old
external FBX2glTF tool is no longer needed)
[2](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html),
[6](https://godotengine.org/article/introducing-the-improved-ufbx-importer-in-godot-4-3/).
`.glb`/`.gltf` remains the recommended, most predictable path
[1](https://docs.godotengine.org/en/4.1/tutorials/assets_pipeline/importing_scenes.html),
so if you can also export GLB from Blender/Maya, send both.

### What to send

| Item | Why |
| --- | --- |
| `.fbx` (or `.blend`/`.glb`) per character archetype | Body, head, hair, boots, gloves, keeper gloves |
| Textures: albedo, normal, roughness/metallic/AO (2K or 4K PNG) | PBR materials |
| Skeleton / bone list + rest pose (A-pose or T-pose) | Retargeting to our 18-bone contract |
| Animation clips (FBX with animation, or separate GLBs) | Run, sprint, pass, shot, tackle, keeper dives, celebrations |
| Poly/tri counts and LODs | Mobile/web budgets |
| Written confirmation you own the files or they are CC0/licensed | We cannot use ripped FIFA/PES assets |
| Kit/team colour requirements, numbering convention | Dynamic kit recolouring |

### The skeleton contract

Our simulation and `RigAnimator` address bones **by name**. The 18 names are:

```
Hips, Spine, Chest, Neck, Head, Face,
LUpperArm, LForearm, LHand, RUpperArm, RForearm, RHand,
LThigh, LShin, LFoot, RThigh, RShin, RFoot
```

Rest pose is 1.80 m tall, local forward `+Z`, up `+Y`, left `-X`, hips at y=0.98.

### Two integration paths

**A — Retarget (fastest, ~1–2 sessions).** Add `Assets/Characters/` +
`Scripts/Godot/ImportedRig.cs` + a `bone_map.json` that maps the FBX bone names
onto the 18 contract names. `RigFactory.Create()` gains a `useImported` switch:
load the GLB, remap the `Skeleton3D` bone names/poses, auto-scale to 1.80 m,
recolor the Shirt/Shorts/Socks material slots from `CharacterSpec`, and keep the
existing `RigAnimator` driving the same bone names. All editor sliders, JSON
save/load, GLB export and match logic keep working unchanged. This gives you
realistic bodies immediately, with our procedural animation still driving them.

**B — Full animation replacement (best looking, larger job).** Replace
`RigAnimator` with an `AnimationTree` state machine using the mocap clips:
locomotion blend space (idle → jog → sprint, strafe, turn), upper-body masked
actions (pass, volley, header, throw), full-body actions (tackle, dive, fall, get
up, celebrate), keeper-specific states, plus `SkeletonIK3D` for foot planting,
ball look-at and hand placement. `RigAnimator.Pose()` becomes a thin adapter that
selects a state from `PlayerState.Action`/velocity. This is where the visual
quality jump really happens — good animation matters more than poly count.

Other work I would add alongside: LOD groups (high poly near, low poly far),
GPU-instanced crowd/subs, kit-number and name decals via dynamic `ViewportTexture`,
hair cards / groom approximations, per-player skin-tone and face variation, and a
validation tool that reports missing bones, >4 weights, bad bind matrices and
texture size before the build.

**Realistic expectation:** imported art will make the characters look like real
footballers. It will not, by itself, deliver licensed teams, stadiums, audio,
motion-capture libraries or AAA lighting — those are separate items in §4.

## 4. Improvements for a modern ("FIFA 26-type") look and feel

Grouped by impact-per-effort. These are genre-standard features implemented with
original assets and code — not copies of any commercial game.

### Phase 0 — cheap, high impact (days)
- Higher-resolution UI with a proper broadcast scorebug, team crests, possession
  bar, momentum graph and shot map.
- Post-processing: FXAA/TAA, tonemapping (ACES), bloom on floodlights, subtle
  vignette, colour grading LUTs for sunny / overcast / night matches.
- Better pitch: normal-mapped grass, anisotropic mowing stripes, wear near the
  boxes, dynamic scuffs and divots, wet-weather reflections.
- Real ball: panel normal map, seam roughness, spin blur, motion trail on shots.
- Goal net as a simulated/vertex-animated mesh that ripples on goals.
- Camera cuts, instant replay, slow-mo and a replay camera (built on the new
  six-view system).
- Crowd ambience + reactions generated procedurally (no licensed audio).

### Phase 1 — characters & animation (weeks)
- Imported humanoid meshes (§3), LODs, kit editor with real fabric materials.
- Mocap-style animation library + `AnimationTree` blend spaces.
- IK foot planting, look-at, head tracking, hand/ball contact.
- Per-player faces, hair, boots, gloves, tattoos; kit numbers and names.
- Cloth/jersey secondary motion (jiggle bones or a light verlet sim).

### Phase 2 — gameplay depth (weeks)
- Timed finishing / timed passing with a visible timing meter and skill ceiling.
- First-touch and ball-control system; close control, shield, knock-on.
- Skill moves mapped to stick gestures (step-over, roulette, heel-to-heel,
  ball roll, fake shot) with stamina cost.
- Richer passes: driven, lofted, threaded, chip, flair, backheel, one-twos.
- Goalkeeper AI: positioning, narrowing angles, punch vs catch, distribution.
- Team tactics: mentality, pressing, defensive line, width, offside trap,
  player instructions, quick tactical presets and formation editor.
- Set pieces: free-kick/penalty aiming with curve, corner routines, throw-in
  movement, walls and decoy runs.
- Matchday layer: referee decisions, VAR-lite review, injuries, substitutions,
  cards, fatigue, morale, commentary text with more context.
- Modes: kick-off, tournament, season, squad building, training/practice,
  penalty shootout, and local 2-player versus.

### Phase 3 — presentation & platform (weeks)
- Dynamic time-of-day/weather, floodlight shadows, volumetric-ish god rays.
- Stadium variety, tunnel/intro sequence, walkout, anthem-style stingers
  (original audio), camera fly-throughs.
- Accessibility: remapping, colourblind palettes, subtitle sizes, one-stick mode.
- Scalable quality presets (Low/Medium/High), 60 fps target on desktop,
  auto-detect on mobile, WebGL quality tier for the browser edition.
- Proper audio: spatial crowd, whistles, boot/ball impacts, net, UI, and optional
  synthetic commentary (no licensed voices).

### Hard limits to be honest about
- The project uses the **Compatibility (OpenGL/WebGL 2)** renderer so one build
  works on web, mobile and low-end machines. That rules out Forward+ features
  (SSGI, SDFGI, volumetric fog, clustered lighting) unless we fork the renderer
  per platform.
- No licensed clubs/players/stadiums/audio/kits, no mocap library, no online
  infrastructure yet, no career/UT-style economy. Those are months of licensed
  content work, not an engine setting.
- We cannot reach parity with a several-hundred-person sports studio. The goal is
  a polished, original, genuinely playable indie football game.

## 5. Making it playable online with friends

> **STATUS (Oct 2026): IMPLEMENTED.** Sections 5.1–5.3 below are now shipped —
> see **`ONLINE.md`** for setup, protocol, verification and limits. Delivered:
> authoritative .NET WebSocket server with room codes/lobby/chat/ping/replays,
> deterministic `StepNetwork`, 20 Hz interpolated snapshots, C# client,
> GDScript WebGL client, local 2-player, Docker/launcher scripts and an
> end-to-end smoke test. What remains from the original plan: NAT hole
> punching / WebRTC P2P, reconnect + host migration, matchmaking, rollback
> prediction, and ranked/async friend features. The rest of this section is
> kept as the original design rationale.

The good news: `Scripts/Core/Match.cs` is a **pure-C# deterministic fixed-step
simulation** with a seeded RNG and no Godot dependency. That is exactly the shape
you want for netcode. `PlayerCommand` is a tiny struct (move, sprint, pass, shoot,
through, tackle, switch, lob, charge) — cheap to send 30–60 times a second.

Godot 4 provides `MultiplayerPeer` with three transports
[1](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html):

| Transport | Where | Notes |
| --- | --- | --- |
| `ENetMultiplayerPeer` | Desktop / mobile native | UDP, lowest latency, reliable + unreliable channels, needs UDP port forwarding for internet play |
| `WebSocketMultiplayerPeer` | Browser clients + server | TCP/WebSocket; browsers have no raw UDP [2](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html) |
| `WebRTCMultiplayerPeer` | Browser ↔ browser | P2P data channels, needs your own signalling + STUN/TURN |

On top of those: `MultiplayerSpawner`, `MultiplayerSynchronizer` and `[Rpc]`
[6](https://generalistprogrammer.com/tutorials/godot-4-multiplayer-tutorial).

### Recommended architecture

**Authoritative server, client prediction, snapshot interpolation.**

```
Server (headless Godot, or plain .NET console running Match.cs)
  - owns MatchEngine, seed, clock, rules, RNG, score, cards, phase
  - receives NetTick{ tick, playerId, PlayerCommand } from every client
  - steps the fixed 60 Hz simulation once all inputs for a tick arrive
  - broadcasts Snapshot{ tick, ball, 22 players (quantised), phase, score }
Client
  - sends its own commands immediately, predicts its controlled player
  - interpolates all other players/ball ~100 ms behind
  - reconciles its predicted player when snapshots arrive
  - renders with the existing rigs/cameras/HUD; only the ring colour changes
```

Why this over pure lockstep: server authority prevents cheating, supports
join-in-progress, 2–8 players, co-op on the same team and spectators, and does
not require bit-perfect determinism across CPUs/framework versions. We can still
**use** the determinism for rollback-lite (re-simulate a few ticks on
mis-prediction) and for exact replay sharing: a match is just
`seed + team sheets + the input log` — tiny files friends can swap.

A pure GGPO-style lockstep/rollback mode is a good later optimisation for 1v1:
it sends almost no state, but needs strict determinism and gets expensive with
many players.

### Friend-first features

1. **Local 2-player on one machine** — split input maps (keyboard + gamepad),
   no networking code needed. Fastest win.
2. **LAN / direct join** — host picks "Create private match", shows a 6-character
   room code and local IP; friend enters it. `ENet`, works offline on a LAN.
3. **Internet friend match** — a small lobby service (HTTPS + WebSocket) maps
   room codes to host addresses, does NAT introspection (UPnP / STUN), and falls
   back to a relay when both players are behind symmetric NAT.
4. **Web friend match** — browser clients connect with `WebSocketMultiplayerPeer`
   to the same authoritative server; no ENet in the browser. The GDScript
   Browser Edition would need its netcode ported, or we ship a thin GDScript
   client that only renders snapshots.
5. **Co-op / clubs** — 2–4 humans on one team, each controlling one player, AI
   fills the rest. Server assigns `controlled` slots.
6. **Async friends** — weekly challenge seeds + replay/ghost upload, penalty
   shootout leaderboards. Cheap, no real-time infra.

unit tests (two engines, 240 identical input frames, identical state hash) but
has not been verified across different CPU architectures or .NET runtimes.
`MatchView` now takes an `IMatchDriver`, so a network input source is injected
cleanly. Online play is shipped and tested; the items in the table below that
go beyond room-code play are still future work.
