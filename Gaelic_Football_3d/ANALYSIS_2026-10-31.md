# Gaelic Football 3D: analysis of gameplay, performance, modelling, rendering and online play (31 Oct 2026)

Basis: a static read of `src/game.c` (2277 lines, engine), `src/main.c` (2075, raylib client), `stadium.c`, `GAMEPLAY_REVIEW.md` and `shared/netplay/`.
`make test` passes here (core rules tests). **raylib is not installed in this container, so I could not run the game or `--bench`.** The performance points below come from reading the code. Measure them with `--bench` / F3 before acting on them.

## 1. Gameplay issues

`GAMEPLAY_REVIEW.md` (R1–R14) is still accurate. Items not yet fixed there, and new ones from this pass:

1. **CPU tackling is the main "unfair" feeling.** `AI_SPEED` is 8.2 m/s, and the player's jog is 7.0 (`PLAYER_SPEED`). A carrier moves at 0.95× of that, so about 6.65 m/s, and sprint is 9.0. The chaser stops 1 m short of a carrier, then commits a tackle after 0.3 s inside 2.2 m (`game.c` ~1295). A tackle's outcome is `frand01`: <0.18 foul, >0.62 miss, else the ball is won. That is a flat roll with no angle, speed or facing input, and no stamina limit on the CPU. The README says "about 80%", but in the code the clean-win rate is about 44% per committed tackle, with a further 18% fouls. The 0.3 s commit makes it feel like 80%, because it re-rolls every 0.9 s (cooldown). Fix R1: weight the roll by approach angle and relative speed, lengthen the commit, cap the chase speed against a carrier.
2. **The engine is hard-wired to "team 0 = the human, team 1 = CPU".** Examples: `players[0][selected_player]`, the `ball_team == 0` tackle check, the single `GameInput` in `game_update`, `has_ball` meaning "team 0 has it", and `update_support_and_marking` only helping team 0. This is the biggest model limit. It blocks two-human play, CPU-attack runs (R9) and symmetrical AI. See section 4.
3. **No stamina, no jockey/contain, no aftertouch, no late pass-receiver lock** (R2, R3, R7, R8, R10). Sprint is free, so there is no pacing and nothing for the defender to do except tackle.
4. **Tuning lives as `#define`s in the engine** (lines 7–19). Move them to a data table (per team/position: speed, kick power, tackle, catch). Positions then differ, which they do not at present, and difficulty becomes a setting.
5. **Frame-rate-dependent play.** `game_update` takes a variable `dt` (clamped to 1/30 in main.c, 0.1 in the engine). Step counting, tackle timers and ball flight are integrated per frame, so a 144 Hz and a 30 fps machine play slightly differently (the 4-step rule counts by distance, which is safer, but the timers are not). Fix: a fixed 1/60 s accumulator and render interpolation (section 4 needs this anyway).
6. **Frontend randomness in the sim path.** `demoInput()` uses `GetRandomValue` (main.c ~820–829), which is fine for the attract mode and not fine if it ever drives a networked CPU. The engine itself uses a seeded LCG in `GameState.rng` (good), but `game_init` seeds it with the constant 12345, so every match opens identically; seed it per match.
7. **Global mutable timing state.** `game_set_action_timing` stores clip contact/duration in file-level statics, set from the loaded animation clips. The sim therefore depends on the animation files. Fine for one machine, but both online peers must have identical clips (put a hash of the table in the checkpoint, as Egyptian Fighter does).

## 2. Performance (to be confirmed with `--bench`)

Likely costs, most valuable first:

1. **One shared `Model`, re-posed and re-drawn up to 31 times per frame.** `drawCharacter` → `poseCharacter` does a bone blend (a 52-bone `QuaternionSlerp`/`Vector3Lerp` on CPU), memcpys the pose, uploads 52 matrices, then issues a `DrawModelEx`. In the GPU skin mode (default) the cost is the per-character uniform upload plus draw-call state changes, not vertices. In the CPU skin mode (F4), ~0.5 M vertices are skinned and re-uploaded per frame; keep that for fallback only.
   - The glb is 11.6 MB. If the mesh is the Meshy-style high-poly it is almost certainly far above what a 30 px tall player needs. Generate **3 LODs** (e.g. ~15k / 4k / 1k triangles) and pick by camera distance; most of the pitch is far away. This is the single biggest GPU win.
   - Better: **GPU instancing with an animation texture** (bake the clips into a bone-matrix texture and draw all players of a kit in one instanced call). It removes the per-character pose and upload entirely. It also fits WebGL2, which matters for the web build below.
   - Skip blending for far or off-screen players (the code already skips off-screen ones).
2. **Planar shadows re-draw the whole skinned mesh** per player (`drawPlanarShadow`, `DrawMesh` for each mesh at Medium). That doubles vertex work at the Medium setting. Use the blob shadow for anyone beyond ~25 m, or render shadows from the LOD1 mesh.
3. **Raw `glClear`/stencil calls and immediate-mode `rlBegin` fans/`DrawCylinderEx` segments for pitch lines and arcs** (lines 397–399, 1264+). Each `DrawCylinderEx` is a batch item. Pre-build the pitch markings into the grass texture (or one static mesh) once.
4. **The crowd is shader-animated and drawn as figures** (good). Check its triangle count; it is probably the biggest static vertex load. Use impostor billboards or an instanced low-poly quad for stands beyond the first rows, especially on Low.
5. **`SetTargetFPS(60)` plus VSync**: on a 144 Hz monitor the game idles at 60 (fine), but `GetFrameTime` jitter feeds straight into the sim (see gameplay issue 5).
6. **Engine O(n²) loops are not the problem.** 30 players with a few nested scans per frame is microseconds. Do not optimise `game.c`; optimise draw calls and vertices.

## 3. Modelling and rendering improvements

**Modelling (engine)**
- Split the engine from "who is human": make `game_update(GameState*, const GameInput in[2], dt)` with a per-team `controlled[team]` (and `human[team]`) and symmetrical AI hooks. This is the prerequisite for online play and for CPU attack logic.
- Replace the flat tackle roll with an inputs-based contest (angle, closing speed, tackler stamina, carrier action). Add stamina, a jockey state, and aftertouch (R2, R8, R10).
- Ball physics: add drag and a Magnus-style curve term so curved kicks (the `curve` field) look right, plus spin on bounces. Use a fixed sub-step (e.g. 4×) for the ball only.
- Move tuning constants into a table loaded at start-up so balance changes do not need a rebuild.
- Add golden-state tests: run N seconds of AI-v-AI from a seed and compare a state hash (the Egyptian Fighter `--sim-test` pattern already in the repo). It protects balance work and is required for lockstep.

**Rendering**
- LODs and instanced animation (above). Add a proper depth-prepass or at least sort opaque draws front-to-back.
- Bake a pitch texture (mowing stripes, lines, arcs, numbers), then use one lit pass. Replace per-frame line geometry.
- Cascaded or at least camera-fitted shadow map for the one directional light (the shadow RT at line ~697 can be fitted to the visible pitch area and given a texel-snapped projection to stop shimmer).
- Post: a cheap FXAA (MSAA 4× is expensive at 1080p+ and unavailable in WebGL1), and a tonemap/vignette for the broadcast look.
- Ball: a motion trail and a distinct shadow ring (high balls are hard to read; AFL reviews note the same).
- Camera: the framing code is sound (`framingTarget`); add the landing marker and nearest marker to the framing box (R13).

## 4. Online play: recommendation

### What the repo already has
`shared/netplay/` is a deterministic lockstep relay: Node server (`relay.js`, `hub.js`, Render deploy), a dependency-free C client (`netplay.c`, WinHTTP / sockets / Emscripten WebSocket backends), rooms with codes and quick-match, input delay chosen from measured RTT, per-30-frame state hashes, drop/rejoin with input replay. Egyptian Fighter and TurboTumble64 already use it. TurboTumble64 proves it works with AI actors sharing the sim.

### Does Gaelic Football fit lockstep? Mostly yes, after one refactor
- `game.c` is pure C with no raylib, a seeded RNG in `GameState`, and the core tests already run it headless. That is exactly the shape lockstep needs.
- Blockers: (a) variable `dt` (fix with a fixed-step accumulator), (b) human = team 0 only (section 3, per-team input), (c) the per-match seed must come from the server's `countdown`/`go` (already supported by the relay), (d) `GetRandomValue` out of the sim path (it already is, apart from demo AI), (e) a `Game_Hash` over 30 players + ball + score + clock + rng for the desync check, (f) global action timings need to match (hash them).
- Bandwidth is trivial: the bit-packed input of 2 humans at 60 Hz. The server is stateless w.r.t. the game, so one free Render instance serves many rooms.
- Trade-off: input delay equals the one-way time plus jitter. At 60–80 ms RTT that is 4–6 frames; fine for a sport game with a heavy character. Above ~150 ms RTT it feels sluggish. Rollback netcode is the upgrade path (the sim state is small, ~30 players × a few dozen floats, so snapshot/restore is cheap), but it needs the engine to be re-entrant and fast-forwardable.

### The "multiple devices" question: ship a web build as the common client
- A native Windows `.exe` and a Linux or Mac build would **not** agree bit-for-bit (`sinf`/`atan2f`/`powf` differ across libms; the netplay README says the same). A **WebAssembly build is deterministic across browsers and devices** (WASM float ops are IEEE-exact, and libm is compiled into the module), so a phone, a tablet, a Chromebook and a desktop can play each other with the same build.
- raylib supports Emscripten/WebGL2 directly, and `netplay_ws.c` already has the Emscripten backend. Work needed: port the custom shaders (skinning, crowd, shadow) from GLSL 330 to GLSL ES 3.00, drop `glClear` stencil calls and `glmin.h` desktop GL usage, preload the assets (11.6 MB glb → compress; use LODs and Basis/KTX2 textures), and add touch controls (two virtual sticks plus action buttons) plus `gamepad` via the browser Gamepad API (raylib maps it).
- Native clients can stay for offline play. For online, use the web build, or a native build whose results are only compared against other builds of the identical binary.

### Alternative: an authoritative server (recommended for phase 2, if you want more than 2 players)
Run `game.c` on the server (native C, or the same wasm in Node) at 60 Hz, send snapshots at 20–30 Hz (30 players + ball ≈ 1 KB), and let clients interpolate and predict only their own player. Pros: no float-determinism worry (any device or native build can join), supports 2v2 up to full 15-a-side co-op, spectators, reconnects with no replay, and cheat resistance. Cons: more server CPU (a Render starter instance holds a few dozen rooms), you need client prediction + reconciliation for responsiveness, and the engine must be refactored the same way (per-team input). Arena FC in this repo already uses an authoritative design with a proxy in the hub, so the hub can host either.

### Recommendation
1. **Phase 1 (≈ 1–2 weeks): 1v1 online via the existing lockstep hub, web build as the cross-device client.**
   - Refactor `game_update` to two inputs; fixed 60 Hz step; `Game_Hash`; per-match seed.
   - Add `gaelic` to `server/games.js` and `hubGames` (path `/gaelic`; picks = team index; `inputKeys` empty like TurboTumble64); add an `online.c` modelled on Egyptian Fighter's.
   - Emscripten build + touch controls; deploy on the existing Render hub, serving the web build as static files.
   - Add a CI `--sim-test` that hashes an AI-v-AI match, run on Linux and wasm (node) to prove cross-platform agreement.
2. **Phase 2 (only if you want 2v2+ or spectators): authoritative server** running the same `game.c`, reusing the hub for routing and rooms.
3. Do **not** add a new transport/framework (Colyseus, Photon, Unity Netcode...): the repo already has a tested relay, rooms, rejoin and deploy config, and WebSocket over TCP is good enough for this game. Consider WebRTC data channels (unordered, unreliable) only if head-of-line blocking over TCP shows up on mobile networks; with lockstep and the existing NACK/resend scheme, TCP is acceptable.

Suggested order of work: sim refactor and hash test → fixed-step loop → LOD/instancing perf pass (needed for phones) → web build → online client → touch controls → balance (R1, R2, R8).
